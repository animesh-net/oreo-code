# Repo conventions

- Never push commits to `main`, including force-pushes. Every change goes on a
  branch and lands through a pull request.
- Branches: new features use `feature/<name_feature>`, fixes use `fix/<name_fix>`.
- No AI attribution anywhere: no Co-Authored-By or session trailers in commits,
  no "Generated with…" lines or links in PR titles or descriptions.
- Never add a "Generated by Claude Code" (or similar) footer to anything:
  PR comments, reviews, review replies, issues or issue comments.
- The posting service may append that footer on its own. After creating a PR
  or posting a comment, read it back from GitHub; if a "Generated by/with
  Claude Code" line (or the `---` rule above it) was added, edit the PR
  description or comment to remove it.
- Commit author: the person whose GitHub account the session is using, never
  Claude.

## Never

- No secrets in the repo. API keys, tokens and passwords never go in code or
  committed files; keep them in untracked local env files or the deployment
  host.
- Never commit a real GitHub token, even in a test.
- No `Co-Authored-By:`, `Co-committed-by:` or any other trailer that names an
  AI agent (Claude, GitHub Copilot, GPT, ...). The git author and committer
  must identify a real person. Agents must not change `user.name` or
  `user.email` in persistent git config; if the environment defaults to an AI
  identity, pass the person's identity per commit
  (`git -c user.name=... -c user.email=... commit`).

## README

- Update `README.md` in the same commit as any user-facing change (behaviour,
  setup, configuration, commands, architecture). A commit that changes
  behaviour without updating the README is incomplete.

## How to edit files

1. Read the full target file before changing it. Never overwrite a file you
   haven't read.
2. Make the smallest change that solves the problem: edit only the lines that
   need to change, don't reformat unrelated code, add comments only when the
   _why_ is non-obvious, and don't introduce new abstractions or refactors
   unless the task asks for them.
3. Run the repo's checks (lint, format, tests) and fix every failure before
   committing. Don't suppress errors.
4. Run `git diff --staged` and scan for secrets (strings like `AIza`, `sk-`,
   `Bearer`, real passwords, env file contents) before committing.

## Commit messages

- One line, present tense, under 72 characters, no body.
- Capitalise the first letter: `Add backup check`, not `add backup check`.
- Be specific about what changed; no filler like "various", "some", "misc",
  "update".
- Never commit WIP.

## Branches

- If a branch was created outside the naming convention (e.g. `claude/...`,
  `fix-...`, `wip`), rename it before pushing more work: `git checkout -b
fix/<name_fix>` from it, push the new name, then ask before deleting the old
  remote branch.

## Pull requests

- Once a branch has no more pending commits, push it and open its pull request
  against `main` straight away; don't wait to be asked.
- Always open pull requests against `main`. Never base one on another feature branch:
  a squash merge deletes that branch and strands or misroutes the pull requests on
  top of it. If work depends on an unmerged pull request, wait for it to merge, or
  branch from `main` and rebase onto `main` once it has merged.
- Title: same rules as commit messages.
- One concern per PR; don't bundle unrelated fixes.
- When several pull requests are open at the same time, no two may change the same
  file. Put every change to a shared file (for example all `README.md` edits) into
  one pull request, or raise the pull requests one after another. This rule wins
  over "one concern per PR" and over keeping a README change in the same pull
  request as the behaviour it describes.
- No commented-out code or leftover debug statements.
- Description structure:

  ```markdown
  ## What changed

  - One bullet per logical change: which file and what behaviour changed

  ## Why

  One or two sentences on the motivation. Link an issue if one exists.

  ## How to test

  Step-by-step instructions a reviewer can follow.

  ## Checklist

  - [ ] PR title starts with a capital letter and is ≤ 72 characters
  - [ ] `npm run check` passes (and `npm run package` if packaging changed)
  - [ ] No secrets committed (checked `git diff --staged`)
  - [ ] No unrelated files changed
  - [ ] No `Co-Authored-By` or AI attribution in commits or this description
  ```

# This repo

oreo-code is a VS Code extension that chats with the models on the Mac's own Ollama
at the `oreo.ollamaUrl` setting, and nothing else: no other server, no sign-in, nothing
leaves the Mac. At activation it lists Ollama's models (`GET /api/tags`) and asks what
each can do (`POST /api/show`), then keeps that list for the session; chats go to
`POST /v1/chat/completions` streamed over SSE, inline completion to the native
`POST /api/generate`. Now: sidebar chat, inline completion, local workspace tools and
agent mode with approval cards and undo; next: the agent's GitHub step (branch,
commit, pull request) through the local `github-mcp-server` over stdio.

## Rules for the code

- **Secrets stay in SecretStorage.** The GitHub token lives only in `src/auth/`.
  Never log it, put it in settings or send it to Ollama.
  `src/auth/ghCliToken.ts` reads the GitHub CLI's token, used only for the release
  check and download in `src/update/`.
- **Model output is untrusted.** The webview renders replies as Markdown only through
  `webview-ui/markdown.ts`: raw HTML off, images off, links limited to http and
  https. Keep the CSP in `src/views/chatViewProvider.ts` strict: no inline scripts,
  no remote content, no `unsafe-eval`.
- **Models come from Ollama.** `OllamaClient.listModels` (`src/ollama/client.ts`) lists
  `GET /api/tags` and builds each model with `modelFrom` (`src/ollama/models.ts`) from
  `POST /api/show`: `tools` → agent mode, `thinking` → the Thinking menu (`levels` for
  gpt-oss, else `switch`; none → no menu and no `reasoning_effort`), the context from the
  Modelfile's `num_ctx` (else `DEFAULT_CONTEXT_TOKENS`, Ollama's 4K default, capped at the
  trained length) → `maxPromptChars` through `promptBudget`; a model without `completion`
  (embeddings) and Ollama's cloud models (`remote_host`/`remote_model`, or a name ending in
  `cloud`; they run on ollama.com) are left out, and one `/api/show` won't describe is offered for plain chat.
  The menu is largest first (`inMenuOrder`); with nothing chosen, `defaultModel` picks the
  largest with tools. No model id is written anywhere in the code. The list is read at
  activation, when `oreo.ollamaUrl` changes, and from the Retry button after a failure,
  never while a session goes on. Every model's `provider` is `macbook`, so the webview's
  picker is unchanged.
- **Completion stays on the Mac.** Inline completion uses only the smallest model with
  `completion: true` (`completionModel(models)`: `insert` capability and a `qwen2` family,
  since the prompt is Qwen2.5-Coder's) on the Mac's Ollama, asking for an 8K context
  (`num_ctx`) on each request; with none installed it's off and the status bar says so. It reads only listed files, never secret files (`isSecretPath`) or
  files the root `.gitignore` ignores, in snippets and the symbol index alike. Its
  size limits live only in `src/completion/budget.ts`; the prompt follows
  Qwen2.5-Coder's repository-level fill-in-the-middle format.
- **Testable core.** `src/chat/`, `src/ollama/`, `src/mcp/`, `src/agent/`, `src/completion/` and `src/update/` have no `vscode` imports; VS
  Code wiring goes in `src/extension.ts`, `src/views/`, `src/auth/` and `src/workspace/`.
- **Agent safety lives in code.** Only the write tools in `ALLOWED_WRITES`
  (`src/agent/catalog.ts`) are offered; a tool without `readOnlyHint: true` is a
  write. `src/agent/policy.ts` refuses writes outside `oreo-agent/` branches and
  pull requests not into `main`, and every write needs approval. Never relax these
  through the prompt.
- **Agent mode writes only with approval.** `runAgent` (`src/agent/loop.ts`) sends
  every write tool through `needsApproval` (`src/agent/policy.ts`): `run_command`
  always asks; `edit_file` and `create_file` ask unless Auto-edit ("Apply edits without asking")
  is on (the default; it and the Agent switch are remembered across reloads in
  `globalState`), which never covers a file that decides what
  runs (`runsCode`: scripts, hooks, build, CI, package lists and settings,
  code-based tool configs and editor task files). The card shows
  the whole change, never a cut one (`MAX_WRITE_CHARS` caps file size instead), and a
  command with hidden or control characters is refused. A rejection goes back to the model; Stop
  counts as one. `writePathProblem` refuses absolute paths, `.`/`..`, `.git` at any depth
  and secret files, in any letter case; the workspace refuses writes through symbolic
  links or outside the folder's real path, checked before the card and again on write; an edit's `old_text` must match exactly once (read_file's `12: ` line numbers are
  stripped if the model copied them; if it still isn't found, a match ignoring whitespace
  (`findIgnoringWhitespace`, at least 12 non-space characters) is used when unique, its new
  lines moved to the file's indentation and deleted lines removed whole, and a
  miss shows the model the closest real lines (`closestText`); in a
  `\r\n` file, with its line endings), checked again when
  applied. Every file is remembered in the task's `Checkpoint` before it changes, so
  "Undo task" can restore it; undo leaves a file alone if it changed after the task
  wrote it, and a task that changes nothing keeps the last task's undo, as does New chat.
  Commands run with `commandEnv`: your environment without VS Code's `ELECTRON_RUN_AS_NODE` and `VSCODE_*`. `fitToContext`
  counts tool-call arguments and trims those of calls already made. Before it, `compactWire`
  (`src/chat/compact.ts`) replaces the earlier conversation with a summary from the model in
  use once the prompt reaches `COMPACT_AT` (95%) of `maxPromptChars`, in chat and agent mode
  alike: the system prompt, the current question and the newest messages (never starting on
  a tool result) stay; the summary is kept for later turns of the chat until New chat; a
  summary that fails or comes back empty leaves the prompt to `fitToContext`, and Stop still
  stops. The summary message tells the model to read a file again before changing it, and the
  agent's record of the files it saw is cleared, since those copies are gone. The chat and
  its summary are saved per folder in `workspaceState` when a turn ends (`chatToSave`, oldest
  turns dropped past `MAX_SAVED_CHARS`) and read back on activation through `readSavedChat`,
  which keeps only well-formed messages; New chat clears it. A tool that fails goes back to the model as an error; the task goes on. Calls get unique ids, unparseable
  arguments are replaced with `{}` in the conversation, and the last round (no tools offered) runs no calls.
  A reply that only announces a next step (`announcesAction`) is not an answer: the model
  is told to do it, up to `MAX_NUDGES` times; a reply that claims changes (`claimsChanges`:
  not negated, not about an earlier task) when the task changed no file and ran no
  command is questioned once, and if it still makes none the reply ends with a note that
  the task didn't change any file. `replace_lines` (by read_file's line numbers; its result
  shows the changed lines with their new numbers) and `write_file` (a whole existing file
  up to `MAX_REWRITE_CHARS`, refusing "rest unchanged" placeholders) become an `edit_file`
  of the whole file, so they share its approval, `runsCode`, Undo and error checks: small
  models (4B and smaller) can't reliably copy exact text. After every change the result ends
  with the file's latest copy, numbered like read_file (`latestCopyNote`, up to
  `MAX_READ_CHARS`), and earlier copies of it in the conversation (read_file results, older
  edit results, whole-file arguments) are replaced with a note (`retireCopies`,
  `src/agent/fileViews.ts`); `replace_lines` and `write_file` on a file that changed since
  the model last saw it (a command or you) change nothing and show the latest copy. Agent calls use `AGENT_TEMPERATURE`
  (0.2) for steadier tool calls. The step limit is `MAX_AGENT_STEPS`, plus `STEPS_PER_FIX`
  for each failed check sent back; ending at it mid-way adds a note saying so. `run_command` refuses commands that only read or list
  files (`READS_FILES`), pointing to read_file, list_files and search.
- **Agent mode ends with working code, on its own.** The root `AGENTS.md`, `CLAUDE.md`
  and `.github/copilot-instructions.md` go in the agent's system prompt, and a folder's
  own `AGENTS.md`/`CLAUDE.md` with the first file read or changed there (`Instructions`,
  within `instructionBudget`). After each edit the result lists the VS Code errors it
  added (`describeProblems`, against the file's errors before the task). When the model
  says it's done and the task changed files, the changed files are checked again (every error left in them
  counts, not only new ones, since a repeated message can hide a new error) and the
  project check from `detectCheckCommand` runs (without one, or if you reject it, `syntaxCheckCommand` parses
  the changed Python files, which runs no code and needs no card; JavaScript is left to
  VS Code's own errors, as `node --check` misjudges JSX and Flow by Node version). When all of
  that passes and the project has a `start` script (`detectStartCommand`, not a watch mode),
  `smokeRun` (`src/agent/smoke.ts`) starts the app for up to `SMOKE_RUN_MS` with a free
  `PORT`, asks for `/` on the port it prints, and fails on a crash, a non-zero exit, a 5xx
  answer or no answer; for a server (`expectsServer`: the task is about serving or the
  project depends on a server framework) exiting at once or nothing answering on its port
  fails too. The process group is killed after. A `run_command` that starts the app
  (`appStartIn`: `npm start`, the start script itself, or anything sent to the background
  with `&` or `nohup`, under endings like `2>&1 || true`) runs the same way instead, after
  its approval card, since a command must end and a server started in the background
  can't be reached; without `smokeRun`, background commands are refused. Failures go back to the model up to
  `MAX_VERIFY_ROUNDS` times, then the reply says they still fail. When a failed check, app
  start or command names a line of a file in the repository (`failureSite`: Node's
  `file:line` above a SyntaxError, the first stack frame outside `node_modules` and Node,
  Python's `File "…", line N`), the message ends with those lines numbered and the failing
  one marked (`linesAround`); a rewrite that then changes nothing gets them again, read
  fresh. None of it needs a
  setting; the project check and starting the app run code the agent may have changed, so
  each asks once per task before its first run (rejecting skips it for that task), then
  runs on its own.
  The check command is never read from settings a repository could set. Agent mode is
  offered only for models with `supportsTools: true`; `find_symbol` reads the one
  symbol index completion keeps, never a second one.
- **Workspace tools only read.** `src/agent/workspaceTools.ts` reads only files in the
  listing (no absolute paths or `..`) and never `.env*`, keys or other secret files,
  in tools or the snapshot. Writes go through the approval flow, never these tools.
- **Pinned MCP server.** `GITHUB_MCP_VERSION` changes only in a PR; the download
  must match the release's SHA-256. The child gets a minimal environment plus the
  token and `GITHUB_TOOLSETS`, never the whole VS Code environment.
- **Errors in one sentence.** Ollama failures are worded in
  `src/ollama/errors.ts`; Ollama answers `{"error":{"message"}}` on `/v1` and
  `{"error":"..."}` on its native API.
- **Packaging.** `@types/vscode` must not be newer than `engines.vscode`; raise
  both together. `.vscodeignore` ships only `dist/`, `media/`, `package.json`,
  `README.md` and `LICENSE`.
- Keep the README short and for developers: how the tool works in a few bullets, its
  prerequisites, the install command, screenshots (`media/screenshots/`) and how to
  develop. Detail on behaviour, settings and code belongs here, not in the README.

## Checks

Run before every commit and fix every failure:

```bash
npx prettier --check .
npm run check      # typecheck (extension + webview), vitest, esbuild
npm run package    # if package.json, .vscodeignore or esbuild.mjs changed
```

A change to agent mode keeps `test/e2e.test.ts` passing (each fixture task must end with
the fixture's own check passing) and adds a case there for any new model behaviour it
handles; `npm run eval` on the Mac measures it with a real small model (`oreo-4b` unless `OREO_EVAL_MODEL` says otherwise).

`.husky/pre-commit` formats staged files with Prettier and checks README links;
`.husky/commit-msg` rejects AI attribution trailers. CI checks the PR title, the
commits, Prettier, the links and the PR description cleaner, then typechecks,
tests and packages the VSIX. The review commands in `.claude/commands/`
(`/full-review` runs them all) check a branch against these rules.

## Things that break if changed

| Thing                                                     | Why                                                |
| --------------------------------------------------------- | -------------------------------------------------- |
| `external: ['vscode']` in `esbuild.mjs`                   | `vscode` exists only at runtime; bundling it fails |
| `retainContextWhenHidden` on the chat view                | Hiding the sidebar would drop a streaming reply    |
| The `oreo.githubToken` SecretStorage key                  | The GitHub token would have to be entered again    |
| `acquireVsCodeApi()` called once (`webview-ui/vscode.ts`) | A second call throws and the webview goes blank    |
