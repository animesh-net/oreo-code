# Repo conventions

- Never push commits to `main`, including force-pushes. Every change goes on a
  branch and lands through a pull request.
- Branches: new features use `feature/<name_feature>`, fixes use `fix/<name_fix>`.
- No AI attribution anywhere: no Co-Authored-By or session trailers in commits,
  no "Generated with…" lines or links in PR titles or descriptions.
- Never add a "Generated by Claude Code" (or similar) footer to anything:
  PR comments, reviews, review replies, issues or issue comments.
- The posting service may append that footer on its own. After creating a PR
  or posting a comment, read it back from GitHub; if a "Generated by/with
  Claude Code" line (or the `---` rule above it) was added, edit the PR
  description or comment to remove it.
- Commit author: the person whose GitHub account the session is using, never
  Claude.

## Never

- No secrets in the repo. API keys, tokens and passwords never go in code or
  committed files; keep them in untracked local env files or the deployment
  host.
- Never commit a real GitHub token, even in a test.
- No `Co-Authored-By:`, `Co-committed-by:` or any other trailer that names an
  AI agent (Claude, GitHub Copilot, GPT, ...). The git author and committer
  must identify a real person. Agents must not change `user.name` or
  `user.email` in persistent git config; if the environment defaults to an AI
  identity, pass the person's identity per commit
  (`git -c user.name=... -c user.email=... commit`).

## README

- Update `README.md` in the same commit as any user-facing change (behaviour,
  setup, configuration, commands, architecture). A commit that changes
  behaviour without updating the README is incomplete.

## How to edit files

1. Read the full target file before changing it. Never overwrite a file you
   haven't read.
2. Make the smallest change that solves the problem: edit only the lines that
   need to change, don't reformat unrelated code, add comments only when the
   _why_ is non-obvious, and don't introduce new abstractions or refactors
   unless the task asks for them.
3. Run the repo's checks (lint, format, tests) and fix every failure before
   committing. Don't suppress errors.
4. Run `git diff --staged` and scan for secrets (strings like `AIza`, `sk-`,
   `Bearer`, real passwords, env file contents) before committing.

## Commit messages

- One line, present tense, under 72 characters, no body.
- Capitalise the first letter: `Add backup check`, not `add backup check`.
- Be specific about what changed; no filler like "various", "some", "misc",
  "update".
- Never commit WIP.

## Branches

- If a branch was created outside the naming convention (e.g. `claude/...`,
  `fix-...`, `wip`), rename it before pushing more work: `git checkout -b
fix/<name_fix>` from it, push the new name, then ask before deleting the old
  remote branch.

## Pull requests

- Once a branch has no more pending commits, push it and open its pull request
  against `main` straight away; don't wait to be asked.
- Always open pull requests against `main`. Never base one on another feature branch:
  a squash merge deletes that branch and strands or misroutes the pull requests on
  top of it. If work depends on an unmerged pull request, wait for it to merge, or
  branch from `main` and rebase onto `main` once it has merged.
- Title: same rules as commit messages.
- One concern per PR; don't bundle unrelated fixes.
- When several pull requests are open at the same time, no two may change the same
  file. Put every change to a shared file (for example all `README.md` edits) into
  one pull request, or raise the pull requests one after another. This rule wins
  over "one concern per PR" and over keeping a README change in the same pull
  request as the behaviour it describes.
- No commented-out code or leftover debug statements.
- Description structure:

  ```markdown
  ## What changed

  - One bullet per logical change: which file and what behaviour changed

  ## Why

  One or two sentences on the motivation. Link an issue if one exists.

  ## How to test

  Step-by-step instructions a reviewer can follow.

  ## Checklist

  - [ ] PR title starts with a capital letter and is ≤ 72 characters
  - [ ] `npm run check` passes (and `npm run package` if packaging changed)
  - [ ] No secrets committed (checked `git diff --staged`)
  - [ ] No unrelated files changed
  - [ ] No `Co-Authored-By` or AI attribution in commits or this description
  ```

# This repo

oreo-code is a VS Code extension that chats with the Oreo models on the Mac's own
Ollama and two Workers AI models through oreo-ai's relay. It calls Ollama directly
(`GET /api/tags` for the model list, `POST /v1/chat/completions` streamed over
SSE) at the `oreo.ollamaUrl` setting. The Cloudflare models go through oreo-ai's
relay on the Pi at the `oreo.cloudUrl` setting (`GET /models`, `POST
/chat/completions`, relayed unchanged to Workers AI with the Pi's token), reachable
over Tailscale only; nothing else of oreo-ai is used: no sign-in. The models are created from the Modelfiles in oreo-ai's
`ollama/` folder. The plan: sidebar chat and a local `github-mcp-server` over
stdio (now), then an agent loop with approval cards, and local workspace tools.

| Path                          | What it is                                                                                     |
| ----------------------------- | ---------------------------------------------------------------------------------------------- |
| `src/extension.ts`            | `activate()`: commands, sidebar view, status bar                                               |
| `src/auth/`                   | Secrets in VS Code SecretStorage (the macOS Keychain)                                          |
| `src/ollama/`                 | Ollama client (OpenAI-compatible), the fixed model list, URL check and error wording           |
| `src/cloudflare/`             | Workers AI client via oreo-ai's relay (model list, thinking, `<think>` filter), error wording  |
| `src/chat/`                   | Chat state and turns; no `vscode` imports, unit tested                                         |
| `src/views/`                  | Webview host, CSP, message relay                                                               |
| `src/mcp/`                    | Pinned `github-mcp-server` download, MCP host and stdio client                                 |
| `src/agent/`                  | Tool catalog (namespacing, read/write, allowlist) and the write policy                         |
| `src/agent/workspaceTools.ts` | Read-only workspace tools (list, read, search); secret files refused                           |
| `src/workspace/`              | The open folder for the snapshot and tools: files, unsaved text, branch, active editor         |

## Rules for the code

- **Secrets stay in SecretStorage.** The GitHub token lives only in `src/auth/`.
  Never log it, put it in settings or send it to Ollama.
  `src/auth/ghCliToken.ts` reads the GitHub CLI's token, used only for the release
  check and download in `src/update/`.
- **Model output is untrusted.** The webview renders replies as Markdown only through
  `webview-ui/markdown.ts`: raw HTML off, images off, links limited to http and
  https. Keep the CSP in `src/views/chatViewProvider.ts` strict: no inline scripts,
  no remote content, no `unsafe-eval`.
- **Cloudflare is opt-in.** Nothing goes to oreo-ai or Cloudflare unless a Cloudflare
  model is picked (only the relay's `GET /models` runs to grey models in or out).
  No Cloudflare token or account id anywhere in the extension: oreo-ai's relay on
  the Pi holds the token, and network access over Tailscale is the access control.
- **Models are named once** in `src/ollama/models.ts` (`OREO_MODELS`); no model id
  anywhere else and no model editing. Display names are `Oreo <size>` (`Oreo 4B`, `Oreo 120B`); a Mac model's id is `oreo-<size>`. Ollama's `GET /api/tags` only marks which
  are installed. The extension only offers a dropdown; agent mode uses only
  models with `supportsTools: true`.
- **Testable core.** `src/chat/`, `src/ollama/`, `src/cloudflare/`, `src/mcp/`, `src/agent/` and `src/update/` have no `vscode` imports; VS
  Code wiring goes in `src/extension.ts`, `src/views/`, `src/auth/` and `src/workspace/`.
- **Agent safety lives in code.** Only the write tools in `ALLOWED_WRITES`
  (`src/agent/catalog.ts`) are offered; a tool without `readOnlyHint: true` is a
  write. `src/agent/policy.ts` refuses writes outside `oreo-agent/` branches and
  pull requests not into `main`, and every write needs approval. Never relax these
  through the prompt.
- **Workspace tools only read.** `src/agent/workspaceTools.ts` reads only files in the
  listing (no absolute paths or `..`) and never `.env*`, keys or other secret files,
  in tools or the snapshot. Writes go through the approval flow, never these tools.
- **Pinned MCP server.** `GITHUB_MCP_VERSION` changes only in a PR; the download
  must match the release's SHA-256. The child gets a minimal environment plus the
  token and `GITHUB_TOOLSETS`, never the whole VS Code environment.
- **Errors in one sentence.** Ollama failures are worded in
  `src/ollama/errors.ts`; Ollama answers `{"error":{"message"}}` on `/v1` and
  `{"error":"..."}` on its native API.
- **Packaging.** `@types/vscode` must not be newer than `engines.vscode`; raise
  both together. `.vscodeignore` ships only `dist/`, `media/`, `package.json`,
  `README.md` and `LICENSE`.
- Commands, settings and install steps go in the README's tables.

## Checks

Run before every commit and fix every failure:

```bash
npx prettier --check .
npm run check      # typecheck (extension + webview), vitest, esbuild
npm run package    # if package.json, .vscodeignore or esbuild.mjs changed
```

`.husky/pre-commit` formats staged files with Prettier and checks README links;
`.husky/commit-msg` rejects AI attribution trailers. CI checks the PR title, the
commits, Prettier, the links and the PR description cleaner, then typechecks,
tests and packages the VSIX. The review commands in `.claude/commands/`
(`/full-review` runs them all) check a branch against these rules.

## Things that break if changed

| Thing                                                     | Why                                                |
| --------------------------------------------------------- | -------------------------------------------------- |
| `external: ['vscode']` in `esbuild.mjs`                   | `vscode` exists only at runtime; bundling it fails |
| `retainContextWhenHidden` on the chat view                | Hiding the sidebar would drop a streaming reply    |
| The `oreo.githubToken` SecretStorage key                  | The GitHub token would have to be entered again    |
| `acquireVsCodeApi()` called once (`webview-ui/vscode.ts`) | A second call throws and the webview goes blank    |
